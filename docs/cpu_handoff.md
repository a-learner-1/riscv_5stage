# CPU 源码交接包（代码准备，尚未导出）

**更新：2026-10-11。** 本步骤新增 CPU 源码交接工具与说明，方便队友取得一个有文件清单、来源记录和哈希的工程副本。本轮只准备源码，未运行导出入口、编译、仿真、PDS 或上板，没有生成交接 ZIP，也没有新增 PASS、性能成绩或五级流水线实现。

交接包用于保留和分享当前代码。包内文件的哈希只能说明文件身份，不能证明设计正确、镜像与当前源码匹配、时序达标或已完成实物验收。

## 导出方式

在 `D:\FPGA\riscv_3stage` 双击 `export_cpu_package.bat`，不带参数时显示中文菜单：

| 输入 | 操作 |
| --- | --- |
| `1` | 导出源码交接包 |
| `2` | 打印导出计划，不生成 ZIP |
| `0` 或直接回车 | 退出，不导出 |

入口需要 Python 3 和 Git。它不会调用 GCC、ModelSim 或 PDS，也不会下载工具、推送 Git 提交或替接收方运行验证。

在 Git Bash 中，可使用以下命令导出：

```bash
cd /d/FPGA/riscv_3stage
cmd.exe //c export_cpu_package.bat --export
```

默认导出已提交的交接文件：已跟踪文件和暂存区必须没有未提交改动，打包范围内的未跟踪文件会阻塞导出。包内源码字节直接读取 `HEAD` 的 Git 对象，可能与经过 CRLF 转换的本机文件字节不同。遇到提示时先查看具体文件，不应仅为消除提示把生成目录或工具二进制加入 Git。

只查看计划：

```bash
cmd.exe //c export_cpu_package.bat --plan
```

`--plan` 只打印计划，不生成 ZIP；它不运行编译或验证，计划也不能作为导出成功记录。

确实需要交接尚未提交的工作区代码时，应显式选择：

```bash
cmd.exe //c export_cpu_package.bat --export --include-uncommitted
```

此选项导出工作区版本，允许包含未提交内容，并在来源记录中如实标明状态。记录的 `HEAD` 只是基线提交，不表示所有打包文件都等于该提交。接收方应同时查看文件清单、工作区状态与各文件哈希。

## 输出与包内容

实际导出后，每次使用独立目录：

```text
build/handoff/<runid>/
├── cpu_source.zip
├── cpu_source.zip.sha256
├── handoff_manifest.json
├── HANDOFF.md
└── package_report.json
```

ZIP 内使用统一根目录 `riscv_3stage/`。旁边的清单、中文交接说明和报告用于核对来源、选择范围、文件哈希及导出结果；`.sha256` 用于检查 ZIP 文件在复制后是否变化。应将同一运行目录内的这些文件一起交给队友。

接收方可解压到自己的英文路径，并替换本说明中的 `D:\FPGA\riscv_3stage`。包内没有 `.git` 历史；构建和仿真入口不要求保留源仓库的 Git 历史，但再次调用导出工具需要位于 Git 仓库中。

包内包含选定的 RTL、固件源码、构建和仿真入口、约束、文档及文本 HEX 初始化文件。工具不会把 `build/`、构建报告、ELF、综合网表、位流、仿真工作库、波形、本机工具库、Git 目录或工具可执行文件带入源码包。

保留文本 HEX 是为了让接收方看到原工程使用的初始化文件。旧 HEX 的存在不代表它由本次源码生成，也不代表当前新固件已经验收。构建来源仍以各版本的有效构建报告和守卫规则为准。

部分 Cache、CoreMark 或板级自检入口要求构建报告、符号文件及镜像匹配。源码包排除了构建报告，因此接收方直接运行这些入口时出现 `BLOCKED` 是预期边界。后续恢复验证时，应按对应说明手动构建所需固件，再使用原守卫检查；不能删除或放宽守卫，把旧镜像当成当前源码的验证结果。统一回归入口的范围和状态定义见 [统一仿真回归说明](regression.md)。

## CNN 集成时采用的 CPU 接口

当前建议从 [soc_axi_lite_top.v](../rtl/soc_axi_lite_top.v) 的 AXI 包装接口接入。它提供 CPU、取指存储器及可选 Cache，数据侧通过 AXI4-Lite 主接口访问外部 RAM 和设备；AXI RAM、地址路由器与 CNN 外设由外围顶层实例化。不要把这个包装模块当成已经包含实际 CNN 的完整系统。

| 项目 | 当前接口或配置边界 |
| --- | --- |
| 指令与软件 ABI | RV32I，ILP32，小端；CSR／中断固件需采用对应的 Zicsr 构建配置 |
| 数据总线 | 32 位 AXI4-Lite，单笔在途事务；AW 与 W 独立握手，不能要求同时到达 |
| 数据读写 | 读返回 32 位字，CPU 处理字节／半字选择；写使用 4 位 `WSTRB` 区分有效字节 |
| 总线功能范围 | 没有 AXI burst、事务 ID 或多笔并发接口；若 CNN 需要批量数据搬运，应另行约定方案 |
| 存储器默认容量 | 指令 ROM 为 8192 个 32 位字，即 32 KiB；数据 RAM 为 4096 个 32 位字，即 16 KiB |
| SoC 地址 | 默认 ROM 从 `0x00000000` 开始，RAM 从 `0x00010000` 开始，16 KiB RAM 范围为 `0x00010000`～`0x00013FFF` |
| 独立 CPU 的差异 | [cpu_top.v](../rtl/cpu_top.v) 的默认 `DMEM_BASE_ADDR` 为 `0x00000000`；不要把独立 CPU 默认值套用到 SoC 集成地址表 |
| 时钟与串口 | 现有专用板级版本使用 50 MHz、115200 波特；通用 SoC 的 `UART_CLOCK_HZ` 默认值是 100 MHz，实例化时必须与实际时钟显式匹配 |
| Cache、BTB | 通用 SoC 默认关闭 I/D Cache 和动态分支预测；启用哪一项必须由实际顶层参数和镜像配置共同确定 |
| 异常与中断 | `ENABLE_TRAPS`、定时器／外部／软件中断默认关闭；启用中断必须同时启用异常处理，并提供对应固件 |
| 复位 | CPU、桥接器、Cache 和 AXI 从设备应使用协调的复位；已经完成的 RAM 写入不会因协议状态复位自动撤销 |
| CNN 地址与格式 | 实际 CNN 寄存器、缓冲区、输入／输出格式和数据搬运方式尚未约定；`0x30000000` 是现有专用演示或统计外设地址，不能直接认定为实际 CNN 地址 |

更换 ROM／RAM 容量时，需要一起修改顶层容量、地址译码、链接脚本、镜像构建与相关检查。仅修改一个 RTL 数组深度不等于软件已经能使用新增空间。

### 中断接入

新外部中断入口是 `irq_external` 电平输入，CPU 使用两级同步。设备应保持中断电平，直到 ISR 清除设备自己的中断源；短脉冲不能假定一定被捕获。三源中断示例的优先级为外部、软件、定时器，分别使用机器模式 cause 11、3、7；这不是已经为真实 CNN 分配好的中断协议。

如果 CNN 队友采用中断完成通知，应共同确定置位条件、清除寄存器、重新触发行为、复位状态和 ISR 操作顺序。新示例及验证待完成范围见 [机器模式外部／软件中断说明](machine_irq.md)。

### Cache 与共享数据

当前数据 Cache 不提供 DMA 一致性协议或外部写入后的失效接口。CNN 若直接写 CPU 已缓存的 RAM，CPU 后续读到的内容可能过期；当前 `FENCE` 行为不能补上缺失的 Cache 失效机制。

初次联调应明确使用不缓存的共享区域，或先关闭数据 Cache；若决定共享可缓存 RAM，需要先设计并验证失效／一致性接口。现有写穿、不写分配的 Cache 行为本身不能证明与 CNN DMA 兼容。细节见 [数据 Cache 说明](dcache.md)。

## 本包能证明什么

| 记录 | 能说明的内容 | 不能据此认定的内容 |
| --- | --- | --- |
| 文件清单和文件 SHA-256 | 本次包内实际选择的文件及其身份 | RTL 功能正确或固件已经通过 |
| ZIP SHA-256 | 收到的 ZIP 是否与导出记录一致 | 包内硬件已完成验收 |
| Git 基线和工作区标记 | 导出采用的提交背景与是否包含未提交内容 | 工作区模式下所有文件都等于 `HEAD` |
| 原项目中的历史验证文档 | 对应日期、配置和证据下的既有结果 | 后续改动、新顶层或新组合自动继承该结果 |
| 包内旧 HEX | 原工程保留的文本初始化镜像 | 当前源码和镜像必然匹配，或当前固件已通过 |

已知历史记录应按具体配置引用：

- 用户在 2026-10-03 提供了 50 MHz、内部 ROM／RAM、无 Cache 配置的 CoreMark performance 与 validation 完整串口日志，均为 `FORMAL PASS`。当时性能基线为 **52.574739 CoreMark、1.051494774 CoreMark/MHz**，见 [CoreMark 说明](coremark.md)。它不是当前 AXI Cache／BTB／中断新组合的成绩，也不是 EEMBC 注册认证结果。
- 定时器中断专用版本在 2026-10-03 有用户实物确认，串口三次输出 `TIMER IRQ PASS`，LED 与 KEY1 现象正常，见 [定时器中断板级说明](timer_irq_board.md)。
- 指令 Cache 专用版本有 2026-10-04 的用户实物确认，完整输出 `ICACHE PASS` 并确认 LED、心跳与 KEY1，见 [指令 Cache 验证记录](icache_verification_20261003.md)。
- [数据 Cache 验证记录](dcache_verification_20261007.md) 中的仿真、PDS／网表记录与实物验收状态应分别阅读；该记录的实物验收仍待完成，不能改写为已经上板通过。
- [BTB](btb.md)、[AXI CoreMark 三配置](coremark_axi.md)、[三源中断](machine_irq.md) 和 [统一回归](regression.md) 的新增步骤按各自文档保留“源码准备、验证待完成”状态。本次源码导出工具也保持相同边界。

接收方复现时应确认收到的版本、实际顶层参数、固件来源、工具版本和目标板卡，再沿用对应检查入口。某一个专用版本的 PASS 不能覆盖另一组参数或另一块板卡。

## 与 CNN 队友的交接内容

交接源码包时，至少同时说明所采用的 SoC 顶层、地址表、时钟、复位、Cache／BTB／异常开关和固件版本。双方还需要确认：

1. CNN 控制寄存器的地址、位定义、字节写支持与错误响应。
2. 输入／输出缓冲区的位置、大小、元素格式、对齐与双方读写权限。
3. 数据由 CPU 访问还是 CNN DMA 搬运，以及是否经过 Cache。
4. 完成状态通过轮询还是中断通知，中断源如何清除。
5. 实际板卡、芯片型号、时钟来源、引脚约束，以及完整系统采用的 PDS 顶层。

这些尚未约定的信息不会由导出工具自动补齐。目前可以交接 CPU 源码和接口说明，但不能宣称已经满足全部 CNN 集成需求。

## 后续改为五级流水线时

五级流水线改造是后续独立工作，本步骤没有实施。如果 AXI、地址表、外设、时钟／复位及中断的软件可见约定保持兼容，CNN 模块通常可以保留；CPU 内部流水线、旁路、暂停和冲刷逻辑需要在独立分支修改，并重新做相应回归。

CNN 的启动、数据访问和完成通知应使用双方约定的寄存器、总线及中断。`pc_x`、`valid_x`、EX／WB 内部层级等观测信号的时序可能随流水线升级变化，应作为调试信息，而不是 CNN 控制协议的触发条件。

即使外部接口保持兼容，完整系统仍需重新集成、综合、检查时序、生成位流并下载验收。现有引脚与时钟约束针对原芯片和板卡，换板或换型号时必须按目标硬件调整；源码包和旧位流不能替代这一步。
